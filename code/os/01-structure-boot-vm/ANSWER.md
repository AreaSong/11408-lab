## 思路

这一关把第 1 章里写不成「算一个数」的三块，收成三条能对答案的路径：服务怎么走、机器怎么把自己拉起来、客户机的特权指令落到谁手里。

### 读文件时差在切换，不差在「有没有文件系统」

宏内核把文件系统放在内核里。用户进程陷入一次，内核里用函数指针直接调用读文件，再返回用户态。模式切换 2 次，函数调用 1 次。`path monolithic` 的 `what=call` 那一行 `switch=no`，就是这次函数调用。

微内核只把中断、原语、进程通信留在内核。文件服务是另一个用户态进程，两边不能直接调用，只能让内核转消息。题目规定的那一趟是：

1. 用户进程把请求交给内核（用户 → 内核）
2. 内核把消息转给文件服务进程（内核 → 用户）
3. 文件服务把结果交回内核（用户 → 内核）
4. 内核把结果送回用户进程（内核 → 用户）

4 次切换，2 条消息，0 次跨进程的函数调用。磁盘驱动如果也是用户态服务，文件服务还得再向驱动发一轮，切换会变成 8 次。考纲拿来和宏内核比性能时，用的是上面这 4 次。

分层结构的各层仍在内核里，所以切换还是 2 次。它慢，是因为系统调用层不能直接叫设备层，必须先叫文件系统层。`path layered` 里没有 `syscall-layer → device-layer` 这一步。

外核也不提供文件抽象。用户进程调用的是用户态的 libOS，这次调用不切模式。libOS 要碰原始磁盘块时陷入外核，外核只检查这块资源是不是分给了它，然后返回。切换也是 2 次，但 `what=check-raw`，内核里没有「读文件」这个服务。

### 引导是四段程序接力

内存里一开始没有操作系统。CPU 上电后从 ROM 里的引导程序开始，每一段只负责把下一段读进来。`boot` 的 7 行对上关卡要求的五件事：

| 行 | 谁在运行 | 从哪读 | 读到哪 | 对应的事 |
|---|---|---|---|---|
| 1 | `firmware` | ROM | CPU | 固件自检 |
| 2 | `firmware` | 磁盘 0 号扇区 | 内存 `0x7c00` | 读引导扇区（MBR） |
| 3 | `disk-boot` | MBR 里的分区表 | — | 找状态字节 `0x80` 的活动分区 |
| 4 | `disk-boot` | 活动分区第一个扇区 | 内存 `0x7c00` | 读分区引导记录 |
| 5 | `part-boot` | 分区里的内核 | 内存内核区 | 装入内核 |
| 6 | `os-init` | 内核 | — | 操作系统初始化 |
| 7 | `os-init` | 内核 | `user:init` | 第一个用户进程 |

2021-46 第（1）问只点四段程序的名字，顺序是 `order` 那一行：ROM 中的引导程序 → 磁盘引导程序 → 分区引导程序 → 操作系统的初始化程序。自检和读 MBR 都算 ROM 里的程序；找活动分区和读分区引导记录都算磁盘引导程序。磁盘引导程序不装内核。

`0x7c00` 是 BIOS 把引导扇区放进内存的约定地址。本机不走这条路径。

制作启动盘是另一条时间线，发生在引导之前。`prep` 的顺序：物理格式化 → 分区 → 逻辑格式化 → 安装操作系统。扇区是物理格式化时划分的；根目录和索引节点表是逻辑格式化时建立的；分区表是分区时写入的。2022-24 问操作系统初始化过程中创建什么：只有中断向量表。BIOS 更早会填一张实模式的中断向量表，题问的是操作系统自己初始化时建的那张。

第一个用户进程在考纲模型里记成 `init`。这台机器的 1 号进程是 `launchd`，见实验记录。

### 主引导记录就 512 字节

| 偏移 | 长度 | 内容 |
|---|---|---|
| 0 | 446 | 引导程序。本关不放 x86 机器码，这 446 字节保持 0，只把位置占住 |
| 446 | 64 | 分区表，4 项 × 16 字节。主分区项只有这 4 个 |
| 510 | 2 | 结束标志，字节必须依次是 `55`、`AA` |

每一项 16 字节里，本关用到的是：第 0 字节状态（`0x80` 活动，`0x00` 不活动），第 4 字节类型（`0` 表示这一项空着），第 8 到 11 字节起始 LBA，第 12 到 15 字节扇区数。LBA 和扇区数是小端。中间 6 个字节是 CHS，考纲不考编码，构造时填 0。

结束标志是这两个字节的顺序，不是把数值 `0x55AA` 按小端写出去。小端写 `0x55AA` 会得到 `AA 55`，`ok` 会是 `no`。没有 `55 AA`，BIOS 不把这个扇区当引导扇区；解析器仍然把分区项读出来，方便看出「标志错了」和「表是空的」是两件事。

类型 `0x05`、`0x0F` 表示扩展分区。逻辑分区记在扩展引导记录里，不在这 64 字节里展开。2021-46 只要求知道分区表记录位置，本关不跟着扩展链往下读。

### 客户机的特权指令不能自己执行

陷入-模拟把客户操作系统降到用户态。它以为自己在内核态，于是执行 `cli`、`in`、`iret`。这些是特权指令，硬件转入虚拟机管理程序。管理程序改的是虚拟机里的状态：`cli` 把虚拟中断标志清 0，`iret` 表示客户内核回到客户用户态，物理 CPU 的最高特权还在管理程序手里。然后回到客户机的下一条指令。普通指令 `mov`、`add` 不陷入，客户机自己执行。

`popf` 用来演示一个漏洞。经典 x86 上，用户态执行 `popf` 改不了中断标志，也不会陷入。它是敏感指令，但不是特权指令。管理程序看不到它，虚拟中断标志保持 `cli` 之后的 0，所以 `effect=missed`。Popek 和 Goldberg 的条件是：敏感指令全都是特权指令，陷入-模拟才可靠。经典 x86 不满足。补救有两条：软件做二进制翻译，或者用硬件辅助虚拟化（Intel VT-x、AMD-V 这一类）让敏感指令在客户模式下陷入。

`hlt` 陷入后虚拟机停机，后面的指令不再取。`traps` 只数真正陷入的次数，`missed` 单算漏掉的敏感指令。

第一类管理程序直接跑在硬件上，自己分原始资源，性能更好，虚拟机要迁走比较麻烦。第二类跑在宿主操作系统上，虚拟磁盘常常就是宿主文件系统里的一个大文件，迁走方便，每一步都要宿主转一手，性能差一档。两类的特权级都高于客户操作系统。第二类有一部分代码以宿主进程的形式待在用户态，截获客户机特权指令时仍要进入更高特权级。2025-24 的 C 对两类都不成立。

## 易错点

1. **微内核的性能比宏内核差。** 2023-23 的第Ⅰ句不成立。可靠性、安全性、可扩展性来自服务放在用户态：一个服务崩溃不一定拖垮内核，加服务也不必改内核。代价是消息和模式切换。
2. **分层结构多出来的是函数调用，不是模式切换。** 层都在内核里，`switches` 仍是 2。不能跨层调用，所以 `calls` 比宏内核多。把「分层」和「微内核」都记成「切换很多」会把 2023-23 的原因讲错。
3. **Linux 的可加载模块仍在内核态，模块之间直接调用。** `struct linux` 是宏内核。它吸收了微内核的一些做法，考纲对比题里不要答成微内核。macOS 的 XNU 才是混合内核：Mach 那一块是微内核，BSD 的不少服务在内核里。
4. **外核没有文件服务，微内核有。** 微内核的文件服务在用户态进程里，用消息通信。外核把原始资源交给 libOS，文件抽象由 libOS 自己做。两者都让内核变小，小的方式不同。
5. **磁盘引导程序不装内核。** 它扫分区表，找到 `0x80` 的活动分区，把该分区第一个扇区里的分区引导程序读进来。装内核的是分区引导程序。四段顺序中间不能把 MBR 和分区引导记录并成一步。
6. **扇区、分区表、根目录不在同一步出现。** 扇区在物理格式化；分区表在分区；根目录和索引节点表在逻辑格式化。有的解析把分区表说成逻辑格式化的产物，和 2021-46 把「分区」「逻辑格式化」分成两步对不上。2022-24 的 C 是分区时建立的。
7. **初始化时创建的是中断向量表。** 根目录、分区表、索引节点表在安装系统之前就有了。BIOS 阶段也会准备中断向量，2022-24 问的是操作系统初始化这一步。
8. **结束标志的字节顺序是 `55 AA`。** 扇区偏移 510 是 `0x55`，511 是 `0xAA`。按小端整数 `0x55AA` 去写，会得到相反的两个字节。
9. **MBR 只有 4 个主分区项，活动分区看第 0 字节是不是 `0x80`。** 类型为 0 的项是空的。空项和「不活动」不是一回事：不活动可以是一个有类型的分区。扩展分区里的逻辑分区不在这 4 项里。
10. **考纲引导模型是 BIOS + MBR。** 本机是 UEFI + GPT，磁盘上没有这份 512 字节的 MBR，`0x7c00` 也不是本机的装入地址。做题走 `boot` 和 `mbr`，看机器走 `EXPERIMENTS.md`。
11. **第二类管理程序好迁移、性能更低，特权级仍然高于客户操作系统。** 虚拟磁盘是宿主上的文件，所以迁走就是拷文件。它要宿主当中介，所以慢。2025-24 的 C 错在「特权级相同」：管不了更高特权，就截不住客户内核的特权指令。
12. **`popf` 不陷入，`cli` 才陷入。** 客户内核用 `popf` 恢复中断标志时，纯陷入-模拟的管理程序不会接手，虚拟标志停留在旧值。这是经典 x86 不能单靠陷入-模拟完成虚拟化的原因。`iret` 会陷入，由管理程序模拟客户态返回，不能把它理解成客户内核拿到了物理机的最高特权。
13. **第一个用户进程在考纲答案里写 init。** 本机 `ps` 看到的 1 号进程是 launchd。两边都对，问的不是同一台机器。

## 概念卡片参考答案

### 卡片一：操作系统结构

| 结构 | 内核里有什么 | 服务怎么找 | 优点 | 缺点 |
|---|---|---|---|---|
| 分层 | 按层放，上层只调相邻下一层 | 内核里的函数调用 | 自底向上好调试，接口固定，好扩充 | 层的边界难划，不能跨层，调用链长 |
| 模块化 | 主模块 + 可装入模块，模块在内核态 | 模块直接调用，不必传消息 | 可并行开发，驱动和文件系统能后装 | 接口难定，模块互相依赖，调试难 |
| 宏内核 | 进程、内存、文件、设备都在内核 | 函数指针直接调用 | 切换少，性能高 | 内核大，一处出错可能整机崩溃 |
| 微内核 | 只留中断、原语、进程通信 | 用户态服务进程 + 消息 | 内核小，服务崩溃不一定拖垮内核，易扩展、易移植 | 切换和消息多，性能低 |
| 外核 | 只分配并保护原始资源，不做文件、页这样的抽象 | 用户态 libOS 自己实现抽象 | 少一层映射，应用程序能自己定抽象 | 一致性弱，libOS 更复杂 |
| 混合 | 微内核的核心还在，一部分服务挪回内核 | 内核里直接调用，也保留消息 | 想要微内核的结构，又想少付切换的代价 | 边界不如纯微内核清楚 |

本关 `struct` 的输出就是这张表压成的键值。`path` 把「服务怎么找」跑成切换次数：宏内核和分层、外核都是 2 次，微内核这一趟是 4 次。

### 卡片二：第一类和第二类虚拟机管理程序

虚拟机管理程序（VMM，也叫 hypervisor）在一台物理机上做出多台虚拟机，每台可以跑自己的操作系统。

| | 第一类 | 第二类 |
|---|---|---|
| 跑在哪 | 直接在硬件上 | 宿主操作系统上面 |
| 谁管物理资源 | 管理程序自己分 | 向宿主要，宿主再分 |
| 客户机的磁盘 | 管理程序划出的一块物理空间 | 常常是宿主文件系统里的一个大文件 |
| 性能 | 更好 | 差一档，多了宿主这一跳 |
| 能开多少台 | 更多，不必和宿主抢 | 更少，宿主和它的进程也要占资源 |
| 迁到另一台机器 | 更麻烦 | 更容易，把镜像文件带走 |
| 特权级 | 最高 | 仍高于客户操作系统；自身代码一部分在用户态、一部分要进更高特权 |
| 常见例子 | Xen、VMware ESXi | VMware Workstation、VirtualBox |

客户操作系统发出的特权指令会被管理程序截住，改成对虚拟硬件的操作，或者在第二类里再变成对宿主的系统调用。管理程序和客户操作系统特权级相同，这件截获就做不成，所以 2025-24 的 C 是错的。

陷入-模拟能工作的前提，是敏感指令都会在用户态陷入。`trap` 里的 `popf` 不陷入，用来记住这个前提。硬件辅助虚拟化给管理程序单独的更高模式（x86 上常说 Ring -1，或 VMX root），敏感指令在客户模式下一律陷入。
