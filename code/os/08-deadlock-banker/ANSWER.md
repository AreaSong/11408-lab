## 思路

死锁是一组进程各自占着资源，又在等这组里别的进程才能引起的事件。四个条件缺一不可：互斥、请求并保持、不可剥夺、循环等待。拆掉任何一条，死锁就组不起来。这是预防。避免不拆这些条件，只是拒绝会走进不安全状态的那一次分配。检测则允许死锁发生，再用化简把环找出来。

### ① Need

`Need = Max − Allocation`。输入写的是尚需时，最大需求是已分配加上尚需，方向相反，结果相同。`load` 把 Need 打出来，就是为了后面每一步都对着这张表，而不是在脑子里减。

已分配大于最大需求是错误数据，`bad-need`。用资源总数时，可用数是总数减去各进程已分配之和；减出负数说明表本身对不上，`bad-total`。

### ② 安全性算法

Work 一开始等于 Available，Finish 全是假。反复找一个 Finish 还是假、并且 Need ≤ Work 的进程，假定它拿齐最大需求后运行结束，把 Allocation 加回 Work，Finish 改成真。全部为真就是安全，顺序就是一条安全序列。有人永远选不出来就是不安全。

同时有好几个人满足 Need ≤ Work 时，安全序列不唯一。本关每次取编号最小的，输出才只有一条。选择题只要选项里有一条走得通，不必等于这一条。`seq` 就是拿选项去试，`count` 把条数算全。条数超过 24 只保留条数和编号最小的那条，2012 年有 66 条，全印出来对做题没有帮助。

`next` 一列是 Work + Allocation。进程结束时还回来的是它占有的全部，不是只还 Need。

### ③ 资源请求

三关，过不了就停：

1. 申请超过自己声明过的 Need，说明它在改口，直接出错，不分配
2. 申请超过现在的 Available，资源不够，进程等待。这还不是不安全
3. 两项都过了，才假装分配：Available 减去申请，Allocation 加上，Need 减去。然后对假装之后的状态重跑安全性算法。安全就答应，不安全就把这次假装作废

`request` 印完就丢掉假装的结果，`applied=no`。同一份 `load` 上可以连续问几次「假如申请这个」。

### ④ 化简

检测用的是此刻的申请边，不是 Max，也不需要知道进程以后最多还要多少。所以银行家算法回答不了「现在是不是已经死锁」。

孤立结点两条边都没有，本来就不在任何环里。其余进程里，谁的当前申请能被现有可用数满足，谁就可以被消去：假定它运行完，Allocation 加回可用。新分给它、让它能够继续的那一份，运行结束时也会还回来，所以 Work 只增加 Allocation。消到没有边剩下，就没有死锁；剩下的进程才是死锁集合。

一类资源只有一个实例时，图里有环当且仅当死锁。有多份实例时，有环只说明可能死锁，必须化简。`practice-graph` 的第二组就是有环但仍能消去：P2 不再申请，先运行结束，把另一份资源还回来，环就断了。

当前申请全是 0 时，每个人都能被消去，因为「再要 0 个」总是满足的。这时系统可以很不安全：他们一旦真的把 Need 都要满，就会死锁。不安全描述的是将来可能走到的坏分配，不是此刻已经互等。`contrast zero` 把这两件事打在一起。

### ⑤ 两种预防

五个人、五根筷子。若让编号最小的人一口气拿完两根，他会吃完，环根本排不出来。`classic` 因此改成全体先拿左手，再各自等右手。等待关系是 P0→P1→P2→P3→P4→P0，四个条件都能看见。

`order` 把两根筷子按编号从小到大申请。P4 的第一根是 0 而不是 4，所以他会空着手等 P0，不会先占住 4。P3 还能拿到空着的 4，吃完把 3 和 4 放下，链从尾巴松开。运行里看得到「拿着一根还在等」，所以请求并保持并没有被拆掉；拆掉的是循环等待，因为大家都按同一个方向要。

`all` 两根必须同时拿到，否则一根都不占。没有人会拿着一根去等另一根，拆的是请求并保持。互斥还在，也没有人中途抢筷子，不可剥夺还在。

### ⑥ 解除

化简之后 `left` 非空，才需要撤销。只在这些进程里还占着资源的那些中间，选代价最小的；代价相同就选编号最小的。王道只说选代价最小，没有规定并列时选谁，编号是为了让输出唯一。

手里是空的人被划掉也不会还回资源，环还在。所以代价更小但没有占资源的等待者不选。`practice-recover` 的第三组就是这个：P0 的代价是 1 但两手空空，撤销的是代价 100、占着那一个资源的 P1。

## 真题在对什么

**2009-25，选 C。** 每人最多 3 台，最坏是每人都已经拿了 2 台。3 个进程占 6 台，还剩 2 台，总有人能拿到第 3 台。4 个进程占满 8 台，谁也拿不到第 3 台，可能死锁。所以可能死锁的最小 K 是 4。`maxn=3` 是保证不死锁的最多进程数，比题目问的那个数小 1。

**2011-27，选 D。** 可用 (0,2,1)，只有 P1 的尚需 (0,0,1) 够。P1 还回 (2,0,0) 后 Work 变成 (2,2,1)，这时只有 P4。P4 还回后是 (2,2,2)，P2 要 3 个 R2，P3 也要 3 个 R2，谁都过不去。不存在安全序列。有的转载把 B、C 两个选项对调了，D 都是「不存在」。

**2012-27，选 D。** 已分配合计 (16,3,19)，可用是 (2,3,3)。Need 是 P0 (2,3,7)、P1 (1,3,3)、P2 (0,0,6)、P3 (2,2,1)、P4 (1,1,0)。

按编号最小走，第一条是 P1 P2 P0 P3 P4，不是选项 D。D 的 P3 P4 P2 P1 P0 单独拿去 `seq`，是安全的。A 第一步 P0 就要 7 个 R3。C 第一步 P2 就要 6 个 R3。B 能先跑完 P1，Work 变成 (6,3,6)，下一步 P0 仍要 7 个 R3，失败。

P3 跑完后 Work 是 (4,3,7)，剩下四个人的 Need 都能单独被这个向量盖住，所以以 P3 开头的 24 条全都安全。以 P4 开头的 24 条也安全。以 P1 开头的有 18 条，因为 P0 不能紧跟在 P1 后面。一共 66 条。题目只问选项里哪一条是安全序列。

标准解析列出的 P4 的 Need 是 (1,1,0)，对应最大需求 (4,2,4)。有的转载把 P4 的 R3 最大需求印成 6。两种表都让 D 安全、A/B/C 不安全。本关跟解析里的 Need。

**2014-24，选 B。** 三人分别还差 1 台就能做完时，已经占了 (3−1)+(4−1)+(5−1)=9 台，再有 1 台就能让其中一人做完。最少是 10。不能按最大的那个需求去套 `3×(5−1)+1`。

**2015-26，选 B。** Ⅰ是顺序申请，那是预防里破坏循环等待的办法，银行家算法不规定申请顺序。Ⅱ对，避免要 Max，检测只看当前的申请和分配。Ⅲ对，避免会拒绝可能导致死锁的分配，检测在分配时不拦。

**2016-25，选 C。** 测试里的那张图化简后剩下 P1、P2、P3，P4 是孤立结点。三个人已经成环。P4 若也在等 R2，化简会把四个人都留下，但题目问的是至少几个，P4 还没申请的那种分配就是 3。

**2018-26，选 A。** 4 个里面已分掉 3 个，可用 1。只有 P3 的尚需是 1。P3 手里本来是 0，还回来之后可用仍是 1。P1、P2 都还要 2，没有安全序列。不存在「先 P3 再 P1」这种序列。

**2019-30，选 B。** 剥夺资源可以解开死锁。预防拆掉必要条件，能保证不发生。银行家算法是避免，不是检测，Ⅲ错。死锁集合里至少两个人互相等，否则形不成环，Ⅳ对。

**2022-26，选 B。** 可用 (1,3,2)，只有 P0 的尚需 (0,2,1) 够。P0 还回 (2,0,1) 后是 (3,3,3)，P1 和 P2 都能接上去。两条：P0 P1 P2，P0 P2 P1。编号最小的那条是前一条。

`practice-request` 用的是常见的五进程例题，Available (3,3,2)。初始就是安全的，编号最小序列是 P1 P3 P0 P2 P4。

- P0 申请 (0,2,0)：没超过 Need，也没超过可用。试分配后的序列是 P3 P1 P0 P2 P4，可以给
- P1 申请 (1,0,2)：也可以给，序列仍是 P1 P3 P0 P2 P4
- P4 申请 (3,3,0)：两类检查都过，但试分配后可用只剩 (0,0,2)，五个人的 Need 都不满足，拒绝
- P0 申请 (0,4,0)：Need 里 B 还有 4，但可用的 B 只有 3，是等待，还没做安全性检查
- P1 申请 (2,0,0)：它的 Need 里 A 只剩 1，是出错

把 (1,0,2) 已经分给 P1 之后，可用变成 (2,3,0)，P1 的 Need 变成 (0,2,0)。这时再来 P0 的 (0,2,0)，试分配得到 (2,1,0)，谁都起步不了，必须拒绝。同是 (0,2,0)，给不给取决于分配之前的状态。

## 易错点

1. 编号最小的安全序列，和选项里那条安全序列，可以不是同一条。2012 就是这样。
2. 不安全不等于已经死锁。安全才一定没有死锁。
3. 银行家看 Need，化简看当前申请。没有 Max 就不能做避免，但可以做检测。
4. 超过 Need 和超过 Available 是两种失败，只有第三步才叫不安全。
5. 试分配被拒绝时，Available、Allocation、Need 都要回到申请之前。
6. 多实例资源有环，仍可能化简成功。
7. 最大需求不相等时，最少资源是 Σ(每个需求 − 1) + 1，不是按最大的那个需求去乘人数。
8. 2009 问的是可能死锁的最少进程数。保证不死锁的资源数是另一问。
9. 撤销只在占着资源的死锁进程里挑。代价小但两手空空的等待者拆不了环。
10. 按序申请拆的是循环等待。一次全要拆的是请求并保持。两件事都没有把筷子变成可共享的。
11. 哲学家若按编号最小一直跑，P0 会吃完，死锁环不会出现。
12. 2011 表上的 (0,2,1) 是系统可用量，不是 P2 私有的一份。

## 概念卡片

| 条件 | 含义 | 预防时怎么破坏 |
|---|---|---|
| 互斥 | 至少有一种资源不能同时给两个人用 | 改成可共享。打印机、筷子做不到，这条通常不拆 |
| 请求并保持 | 占着一些，还在等另一些 | 一次申请全部，要不就一根都不占 |
| 不可剥夺 | 只能自己用完放开，不能被抢走 | 等资源时先放下已经拿到的。抢占式分配 |
| 循环等待 | 等待关系首尾相接 | 给资源编号，只许按编号递增申请 |

| 策略 | 何时 | 要不要 Max | 结果 |
|---|---|---|---|
| 预防 | 申请规则事先定死 | 不要 | 四个条件少了一条，能保证不死锁，利用率低 |
| 避免 | 每一次分配之前 | 要 | 拒绝不安全的分配。安全序列不唯一，也不是进程必须遵守的顺序 |
| 检测并解除 | 分配时不拦，事后化简 | 不要 | 发现环再剥夺、撤销或回退。本关按撤销代价最小 |

死锁是这一组进程都在等本组其他人。饥饿是别人还在往前走，某一个进程一直轮不上。资源不够会造成饥饿，单独这一条并不构成死锁。

安全：至少存在一条序列，按这条序列把每个人的最大需求都满足，所有人都能做完。系统若停在安全状态，就还有办法避开死锁。

不安全：这样的序列一条都没有。进程若把剩余的 Need 都要满，分配可能走进死锁；它们若根本不再申请，此刻也可以还没有死锁。

已经死锁：化简消不干净。这时一定不安全，但反过来不成立。
