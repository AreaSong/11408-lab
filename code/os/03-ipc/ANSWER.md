## 思路

进程的地址空间是隔开的。通信就是请内核开一扇受控的窗：要么让两边的页表指向同一块物理页，要么让内核把字节从一边拷到另一边，要么只敲一下「有事了」。

### 四种方式差在谁搬数据、谁管顺序

| 方式 | 数据怎么到对方手里 | 顺序谁管 | `mode` |
|---|---|---|---|
| 共享存储区 | 建立映射之后，两边直接读写同一块物理内存 | 用户自己用同步工具 | `shared` |
| 消息传递 | `send` / `receive`，内核拷贝一条有边界的消息 | 原语可以阻塞 | `message` |
| 管道 | 写进内核里一块内存缓冲，另一端再读出来 | 写满阻塞、读空阻塞 | `pipe` |
| 信号 | 不搬缓冲区，只递一个信号编号 | 异步，处理函数什么时候跑由内核决定 | `signal` |

`kernel=setup` 只给共享存储。内核做的是把页表指过去。指完以后，这一次通信的读写不再陷入内核。消息、管道、信号都是 `kernel=every`：每次传递都要进内核。

`bulk=yes` 表示这件事是用来搬数据的。它不表示缓冲区无限。管道的缓冲是内存里固定的一块，写满就堵，见 `pipe` 的 `full` 和 `block`。信号是 `bulk=no`。

需要自己处理同步的是共享存储。`card` 里只有 `shared` 的 `sync=user`。管道和消息传递把「空了等、满了等」做进读写真或收发原语里，`sync=os`。信号不负责给一批数据排先后，`sync=async`。

### 管道是半双工的字节流

2014-31 的四句，只有 C 是对的：读和写都可能阻塞。

A 不对。王道把管道记成半双工：同一时刻一个方向。双向同时传，要两条管道。`pair` 就是这个：`ping` 走第一条，`pong` 走第二条，`pipes=2`。`mode pipe` 的 `duplex=half`。

POSIX 的匿名管道比「半双工」还死一点：创建之后写端和读端的方向就是固定的，不能把同一条管道反过来用。王道和 2014-31 的标准答案仍然叫半双工，意思是「一个管道不能实现双向数据传输」。本关按这个口径，不把管道改写成全双工，也不改成和标准答案相反的单工。全双工的是 `msg` 那一对套接字。

B 不对。缓冲在内存里，`medium=memory`。不是磁盘文件，容量也不随磁盘变大。解析里常写「通常是内存中的一页」。本机这次测到的字节数在 `EXPERIMENTS.md`，不要把它背成页大小。选项错在「仅受磁盘容量大小限制」。

C 对。`empty` 和 `full` 用非阻塞看到 `EAGAIN`：内核拒绝这次调用，等于说「若阻塞着做，你会睡在这里」。`block read` 和 `block write` 真的睡下去，再用 50 ms 重复触发的 `SIGALRM` 打断。没有 `SA_RESTART`，所以 `read` / `write` 返回 `EINTR`，输出 `blocked=yes`。

这里有一个前提，和 C 的字面容易拧在一起。`block write` 时读端必须还开着。读端全关，写端收到的是 `SIGPIPE`（本关把它忽略成 `EPIPE`），进程不会睡在 `write` 里。`block read` 时写端必须还开着，否则 `read` 得到文件结束，也不是阻塞。2014-31 的 C 说的是两端都还在、缓冲空了或满了的那种阻塞。

D 不对。一个管道可以有多个读进程或多个写进程，同时写要互斥。不是「只能有一个读的或一个写的」。`claim pipe-one-end` 是 `false`。

`stream` 把 `ab` 和 `cd` 分成两次 `write`，子进程一次读出 `abcd`。管道是字节流，不保留消息边界。`claim pipe-boundary` 是 `false`。数据一旦被读走，就不再留在缓冲里，所以子进程要靠另一条管道把读到的字节送回父进程。

匿名管道的文件描述符靠 `fork` 继承，没有亲缘关系就拿不到同一对端口，`kind anon` 是 `kin=yes`。命名管道（FIFO）在文件系统里有名字，无亲缘的进程也能 `open`，仍然是半双工字节流，`kind fifo` 是 `kin=no`。所以 `mode pipe` 的 `kin=either`，不要写成一个笼统的 yes。本关实验只做匿名管道，不创建 FIFO 文件。

### 共享存储快，是因为后来不再拷贝

`shm` 在 `fork` 之前 `mmap`。`MAP_SHARED` 让父子的这块虚拟地址落到同一物理页。父进程在 `fork` 之后写入 408，用管道字节告诉子进程「可以看了」。子进程看见 408，写入 11408。父进程再从映射里读到 11408，`shared=yes`。

这个字节不是共享内存的一部分。映射不会等你写完。两个进程同时读写同一块，可能读到写了一半的数。王道因此要求使用同步互斥工具。本关用管道字节把先后排开，`sync=user`。第 06 关再用信号量做这件事。

`MAP_PRIVATE` 用同一套握手。父进程在 `fork` 之后写 408，写的是自己的私有页。子进程看见的仍是 0，自己写的 7 也回不到父进程的页上。7 能出现在输出里，是因为它走了管道，不是因为它走了映射。`parent-saw=0`，`shared=no`。

`kind region` 是高级的共享存储区，`bulk=yes`。`kind struct` 是低级的共享数据结构：程序员自己在共享区里放一个定好的结构，只适合少量数据，`bulk=no`。`mode shared` 按共享存储区填。

2025-30 的第 I 项说内存映射文件可以实现进程间通信。多个进程对同一个文件做共享映射，页表指向同一批物理页，这就是共享存储的一种。`claim mmap-ipc` 是 `true`。II、III、IV 问的是页面和磁盘块、虚拟地址还是物理地址，本关不判断。第 11 关做内存映射文件的实验。

### 消息传递保留边界

直接通信：发送进程点名接收进程，消息挂到对方的消息缓冲队列。`kind direct` 是 `target=pid`。

间接通信：消息放进信箱，接收进程从信箱取。双方不必点名对方。`kind mailbox` 是 `target=box`。

本机没有单独的信箱系统调用。`socketpair` 的 `SOCK_DGRAM` 让一次 `send` 对应一次 `recv`，用来看「有边界」这件事。父进程连发 `ab` 和 `cd`，子进程两次 `recv` 得到两条，而不是 `abcd`。`boundary=yes`，`claim message-boundary` 是 `true`。

`both` 在同一对套接字上先发 `ping` 再收回 `pong`。这是全双工，`duplex=full`。不要用这个结果去改管道的半双工。

消息原语可以是阻塞的：对方还没发，`receive` 就等。同步做在原语里，`sync=os`。用户不必再为「这块共享内存有没有写完」配一把锁。原语也可以选成非阻塞，那是另一套接口；408 拿来和共享存储对比时，要自己另配 PV 的是共享存储。

### 信号只敲一声

`usr1` 和 `term` 都装了处理函数。父进程等子进程声明准备好再 `kill`。子进程先屏蔽该信号，再用 `sigsuspend` 放开，这样信号在等待之前到达也不会丢。处理函数把 `sig_atomic_t` 设成 1。`printf` 不是异步信号安全的，不能放进处理函数。

`caught=yes` 且 `default=no`：处理函数跑了，进程是自己 `_exit(0)` 的，不是被默认动作杀掉的。`SIGTERM` 的默认动作是终止，但捕获之后可以不终止。`payload=no`：这次只送了编号。

`SIGKILL` 和 `SIGSTOP` 不能捕获、不能忽略、不能屏蔽。`kill` 里 `sigaction(SIGKILL)` 失败，子进程停在 `pause`，父进程再发 `SIGKILL`，`wait` 看到的是「被信号终止」。`caught=no`，`default=yes`。`claim sigkill-catch` 和 `claim sigstop-catch` 都是 `false`。`claim sigterm-catch` 是 `true`。

`merge` 在子进程还屏蔽着 `SIGUSR1` 时连发 1000 次。普通信号在内核里是一位未决标志。已经未决时，再来的同号信号被丢掉。放开之后处理函数只进一次，`got=1`，`queued=no`。所以信号既搬不了大量数据，也不能当作可靠的计数器。

信号和信号量不是一个词。信号量是一个整数，P/V 用来同步和互斥。英文教材里 V 操作有时也叫 signal，和这里的 `kill` / `sigaction` 无关。

### 1 MB 的时间差在拷贝，不在信号

`bench` 从对方准备好开始计时，到对方收齐为止，不含 `fork`。管道和字节流套接字都要把 1 MB 拷进内核再拷出来。共享内存是父进程 `memcpy` 进映射，再用原子标志叫醒子进程，子进程直接核对那一块。连续几次运行里，共享内存都比管道短，管道都比套接字短。1 MB 还小，调度会把差距晃来晃去。具体微秒数在 `EXPERIMENTS.md`。

信号那一行是 `bytes=0`。200 次来回每次都等确认，所以不会像 `merge` 那样合成一次。这 200 次只证明通知要进内核，不能拿来和 1 MB 的拷贝比「谁更快」——它们搬的不是同一件东西。

## 易错点

1. **管道按王道和 2014-31 记半双工。** 双向用两条。`socketpair` 能在一条通道上两个方向发，那是消息实验，不是管道。
2. **写满才会阻塞，读端被关不会。** 读端全部关掉，写是 `SIGPIPE` / `EPIPE`。2014-31 的 C 要求两端都还在。
3. **读空才会阻塞，写端被关不会。** 写端全部关掉，`read` 得到 0，表示没有后续数据。
4. **非阻塞的 `EAGAIN` 和真的睡着不是同一行输出。** `full` / `empty` 是内核拒绝。`block` 才是调用已经进了内核、被闹钟打断。
5. **管道不保留边界。** `ab` 加 `cd` 可以一次读成 `abcd`。消息的数据报不会这样粘。
6. **容量在内存里，不在磁盘上。** 不要把「通常约一页」背成选项 B。本机缓冲有多大，看 `EXPERIMENTS.md` 的 `pipe-capacity`。
7. **匿名管道要亲缘，命名管道不要。** `mode pipe` 因此是 `kin=either`。两条都仍然是半双工字节流。
8. **共享映射不会自己等。** `sync=user`。只 `mmap` 不安排先后，子进程可能读到旧值。`MAP_PRIVATE` 在 `fork` 之后的写入对方看不见。
9. **`mode shared` 是共享存储区，不是共享数据结构。** 后者是 `kind struct`，`bulk=no`，只适合少量数据。
10. **2025-30 的第 I 项是通信，第 II 项有争议。** 本关只锁定「可以用来进程间通信」。页面和磁盘块的方向不要在这里提前写成一句死的 `false`。
11. **信号不是信号量。** `sigterm-catch true` 说的是进程可以捕获 `SIGTERM`。它不是 V 操作。
12. **`SIGKILL` 装不上处理函数。** 子进程若因为 `sigaction` 失败就自己退出，父进程就看不见「被信号终止」。要停住，等父进程来杀。
13. **普通信号不排队。** 屏蔽期间连发 1000 次 `SIGUSR1`，放开后处理函数进一次。不能用信号个数当收到的字节数。
14. **处理函数里不要 `printf`。** 它可能正被信号打断，内部状态不是可重入的。只写 `sig_atomic_t`，结果由正常的执行流打印。
15. **1 MB 的计时不能用来证明信号很慢。** 信号那一行的字节数是 0。和管道比时间之前，先看 `bytes`。
16. **映射地址相同，不表示两块是共享的。** `shared` 和 `private` 各做一次，`munmap` 之后下一次可能分到同一个虚拟地址。看 `parent-saw`，不看地址字面。

## 概念卡片参考答案

### 卡片：四种进程通信

| | 共享存储 | 消息传递 | 管道 | 信号 |
|---|---|---|---|---|
| `mode` 的名字 | `shared` | `message` | `pipe` | `signal` |
| 每次传递是否经过内核 | 建立时经过，之后用户态读写 | 每次都经过 | 每次都经过 | 每次都经过 |
| 同步 | 用户自己做 | 操作系统在原语里做 | 操作系统按空和满阻塞 | 异步通知 |
| 适合的数据量 | 大量 | 能搬，有一次消息的上限 | 能搬，缓冲有上限 | 只有一个编号 |
| 方向 | 双方都能读写 | 双方都能收发 | 半双工，双向要两条 | 通知，没有数据通道 |
| 边界 | 没有固定消息，自己约定结构 | 有，一次收一条 | 没有，字节流 | 没有数据 |
| 是否要求亲缘 | 不要求 | 不要求 | 匿名管道要求，命名管道不要求 | 不要求，但要有发送权限 |

`card` 按这四行的顺序输出，字段是 `duplex`、`kernel`、`sync`、`unit`、`bulk`、`kin`、`medium`。`kind` 把共享存储再分成低级结构和高级存储区，把消息传递再分成直接通信和信箱，把管道再分成匿名和命名。
