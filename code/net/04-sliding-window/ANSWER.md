## 思路

### 停等就是窗口为 1 的 GBN

发完一帧必须停下来等它的确认。超时只重传这一帧。1 位序号就够：窗口里永远只有 0 或 1，重传不会和新帧用同一个号。`tests/practice-stop` 里，0 确认之后才能发 1；1 丢掉之后超时仍是重传 1，左边界不动。确认回来，序号绕回 0，队列里 `front` 和 `rear` 又碰到一起，队空。

信道利用率

U = Td / (Td + Ta + 2 × 单向传播)

`tests/util/practice-stop` 的数据帧是 1000 bit，带宽 10 kbps，单向传播 200 ms，确认帧长度是 0。Td = 100 ms，周期 = 100 + 0 + 400 = 500 ms，U = 20%，平均速率 = 1000 bit / 0.5 s = 2 kbps。一个周期里只发了 1 帧，信道有 400 ms 是空的。

窗口加大以后，一个周期里可以连续发 W 帧：

U = min(1, W × Td / 周期)

W × Td ≥ 周期时第一个确认回来，发送方还没把窗口发完，U 封顶为 1。上面那条链路要 W ≥ 500 / 100 = 5 才用得满。停等做不到，GBN 用 5，序号至少 3 位（2²−1 = 3 不够，2³−1 = 7 够）。

### 2009-35：没看见 ACK 1，不代表 1 号帧没到

GBN 的接收窗口是 1。失序帧直接丢掉，并且只给最早未确认的帧挂一个计时器。超时就从这一帧起，把队列里已经发出去的帧全部重传。

ACK n 是累计的：n 以及窗口里它前面的帧都算收到了。发送方已经发出 0～7，超时前手里只有 ACK 0、ACK 2、ACK 3。ACK 1 丢在回来的路上。ACK 2 到的时候，左边界还是 1，累计确认把 1 和 2 一起滑出去；ACK 3 再把 3 滑出去。左边界停在 4。重传的是 4、5、6、7，一共 4 帧，选 C。

重传 5 帧是把已经确认的 3 又算了进去。重传 3 帧是漏看了累计，以为 1 号帧也要重传。

### 2011-35 和 2024-37：SR 谁超时重谁

SR 的 ACK n 只确认 n，没有累计作用。接收方可以先收下窗口里的失序帧，等缺口补上再按顺序交给上层。每个未确认帧各有一个计时器。

2011 已发送 0～3，只收到 ACK 1。0 和 2 超时。ACK 1 不能把 0 带走，左边界仍是 0，所以 0 要重传；2 超时，也要重传；3 题目没说超时，不重传。一共 2 帧，选 B。

2024 的序号是 3 位，收发窗口相等且最大，所以两边都是 4。甲先发出 F0～F3，F1 丢失。t1 收到 ACK 0，左边界从 0 滑到 1，空出一个位置，新帧是 F4。之后 ACK 2 只给 2 记账，1 还没确认，窗口不能再滑，F5 发不出去。t2 是 F1 超时，只重传 F1。t1、t2 发出的是 F4、F1，选 D。

发出 F4 的时候队列绕了回来：`front = 1`，`rear = 0`，格子是 `[_ 1 2 3 4]`。`rear` 指着的那一格是空位，不是最后一帧。

`tests/practice-sr-fill` 把同一件事走到尽头：2 和 3 先缓存、先单独确认，1 到达之后接收方把 1、2、3 一起上交；发送方收到 ACK 1 时，2 和 3 已经记过账，左边界从 1 直接滑到 4。

`tests/practice-gbn-loss` 是对照。2 号帧丢掉，3 和 4 先到。GBN 不缓存，两帧都丢，超时从 2 起重传 2、3、4。SR 在同样的局面里只会重传 2。

### 窗口上限：空一个序号，是为了分清新旧帧

n 位序号，序号空间 N = 2ⁿ。

| 协议 | 发送窗口 | 接收窗口 |
|---|---|---|
| 停等 | 1 | 1 |
| GBN | 1 ～ N−1 | 固定 1 |
| SR | 与接收窗口之和 ≤ N，且接收窗口 ≤ 发送窗口 | 相等时各是 N/2 |

GBN 不能把 N 个序号都放进发送窗口。Ws = N 时，0～N−1 全部发出，确认全丢，发送方重传 0；接收方已经在等下一轮的 0，分不清这是旧帧还是新帧。空出一个序号，最大就是 N−1。3 位时 GBN 最大 7。

SR 收发窗口相等时，每个最大 N/2。3 位时是 4。两边都取 5，接收方确认了 0～4 并滑到 5、6、7、0、1 之后，0 的确认若丢失，重传的 0 会落进新窗口，被当成新帧。

2019-35 的题面只写「滑动窗口」，发送窗口是 5，3 位序号。选项里没有 1，不是 GBN（GBN 的接收窗口恒为 1）。按 SR：Wr ≤ Ws，并且 Ws + Wr ≤ 8。Wr ≤ 5，同时 Wr ≤ 8−5 = 3。更紧的是 3，选 B。

2023-35 不给链路参数，比的是最大利用率。没封顶时 U 随 W 增大，封顶之后再加大窗口也不再升高，所以上限就看最大窗口：停等 1，SR 4，GBN 7。U1 ≤ U3 ≤ U2，选 B。三个窗口里只要有相等的，对应的 ≤ 就取等号，方向不变。

### 2012-36：按最短的帧来要窗口

确认帧和数据帧等长，Ta 不能扔。帧越短，Td 越小，一个周期里能塞进的帧越多，需要的窗口越大。范围内两种长度都要达到最高利用率，就看 128 B。

128 B = 1024 bit，16 kbps，Td = Ta = 64 ms，往返传播 540 ms，周期 668 ms。668 / 64 = 10.4375，窗口至少 11。GBN 要求 2ⁿ−1 ≥ 11。n = 3 时最大 7，不够；n = 4 时最大 15，够。选 B。

512 B 的 Td = Ta = 256 ms，周期 1052 ms。1052 / 256 = 4.109375，程序按四位小数印成 4.1094，向上取整仍是 5。这一档 3 位就够，但盖不住短帧，所以不起决定作用。

只拿长帧去算会得到 3 位，那是选项 C。把 SR 的「窗口不超过序号空间一半」用到 GBN 上，2ⁿ⁻¹ ≥ 11，会得到 5 位，那是选项 A。

### 2014-36：先看有没有封顶

1000 字节是 8000 bit，100 Mbps，Td = 0.08 ms。确认帧的发送时延忽略，单向传播 50 ms，周期 = 0.08 + 100 = 100.08 ms。

用满信道要 W ≥ 100.08 / 0.08 = 1251。题目的窗口是 1000，比 1251 小，确认回来之前窗口已经发完，后面有一段空闲。一个周期发出 1000 × 8000 = 8×10⁶ bit，平均速率 = 8×10⁶ / 0.10008 s = 79.936 Mbps，离 80 Mbps 不到 0.5，记成约 80 Mbps，选 C。直接答 100 Mbps 是没做「窗口够不够把信道填满」这一步。

### 2015-35：80% 先求出窗口，再求位数

1000 字节、128 kbps，Td = 62.50 ms。不考虑确认帧，周期 = 62.50 + 500 = 562.50 ms。

W × 62.50 / 562.50 ≥ 80%，W ≥ 7.2，至少 8。完全用满要 9，题目只要 80%，窗口就是 8。

题面没有点名协议。GBN：2ⁿ−1 ≥ 8，n = 3 时最大 7，不够，n = 4 够。SR 两边相等：2ⁿ⁻¹ ≥ 8，n = 3 时最大 4，也不够，n = 4 够。两种都是 4 位，选 B。只按「序号空间 ≥ 窗口」得到 3 位，那是选项 A，把 GBN 的减 1 和 SR 的一半都漏了。

## 易错点

1. **ACK n 在王道里表示 n 号帧已收到。** 不是「下一帧期待 n」。两种约定差 1，累计确认会整段滑错。
2. **GBN 的确认是累计的。** 2009 没收到 ACK 1，但 ACK 3 已经把 0～3 都确认了。要重传的是 4～7。
3. **SR 的确认不累计。** 2011 的 ACK 1 留不住 0。3 没有超时，也不重传。
4. **GBN 最大窗口是 2ⁿ−1，不是 2ⁿ。** SR 两边相等时每个是 2ⁿ⁻¹。2019 还要再和 Wr ≤ Ws 取更紧的一条，5 和 8−5 里更紧的是 3。
5. **先判断窗口有没有把信道填满。** 2014 的 1000 < 1251，速率约 80 Mbps，不是带宽 100 Mbps。
6. **帧长给了范围，按最短的那一档。** 2012 的 512 B 只要 3 位，128 B 要 4 位。确认帧等长时 Ta 和 Td 一样，都要加进周期。
7. **2015 的 7.2 要向上取整成 8。** 题面没点名协议时，GBN 和 SR 都要装得下这个窗口，两边都是 4 位。
8. **GBN 只有一个计时器，挂在最早未确认的帧上。** 超时重传的是从它起到队尾的全部帧。SR 是谁超时重谁。
9. **失序帧：GBN 丢掉，SR 缓存。** 同一组「2 丢失、3 和 4 先到」，GBN 重传 2、3、4，SR 只重传 2。
10. **循环队列的 rear 是空位。** 2024 发出 F4 之后 `rear` 绕回 0，最后一帧在它前面那一格。

## 概念卡片参考答案

### 卡片一：流量控制和可靠传输

| | 要解决的事 | 靠什么发现 | 窗口在其中的角色 |
|---|---|---|---|
| 流量控制 | 发送方别发得比接收方处理得快 | 接收窗口、确认 | 接收方告诉发送方现在还能收多少 |
| 可靠传输 | 帧或确认丢了，数据还要送到 | 序号、超时、确认 | 发送方记住哪些帧还没被确认，超时再发 |

滑动窗口两件事都用它，但题目问「为什么重传」时答的是可靠传输，问「为什么不能一直发」时答的是流量控制。停等把两件事都做成了窗口 1：对方没确认，既可能是没收到，也可能是还来不及收，发送方一律停住。

### 卡片二：停等、GBN、SR

| | 停等 | GBN | SR |
|---|---|---|---|
| 发送窗口 | 1 | 最大 2ⁿ−1 | 与接收窗口之和 ≤ 2ⁿ；相等时最大 2ⁿ⁻¹ |
| 接收窗口 | 1 | 1 | 通常与发送窗口相同，且不超过发送窗口 |
| 确认 | 一帧一确认 | 累计确认 | 逐帧确认 |
| 失序帧 | 不连续发送 | 丢掉 | 先缓存 |
| 计时器 | 当前这一帧 | 只挂最早未确认的帧 | 每个未确认帧一个 |
| 超时 | 重传这一帧 | 从它起全部重传 | 只重传超时的帧 |
| 接收缓存 | 不用 | 不用 | 要 |
| 误码高时 | 一次只白费一帧 | 一帧出错会连累后面已正确到达的帧 | 只补真正丢的那一帧 |

3 位序号时，三个最大窗口是 1、7、4。没把信道用满之前，最大利用率也是这个顺序：停等 ≤ SR ≤ GBN。窗口大能提高无差错时的利用率，同时放大 GBN 一次丢帧的重传代价。误码高到几乎每个窗口都丢一帧时，GBN 可能反而不如停等，这时才显出 SR 的好处。
