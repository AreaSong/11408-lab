## 思路

### 校验和为什么要回卷再取反

把要保护的字节按 16 位、大端分成字，加起来。超过 16 位的进位加回最低位，这是反码加法，不是把进位丢掉。全部加完再按位取反，得到校验和。

2024-39 只给了最后两个字：

```
  1011 1001 1011 0110
+ 0110 0101 1100 0101
= 1 0001 1111 0111 1011
```

低 16 位 `0001 1111 0111 1011` 加上进位 1，是 `0001 1111 0111 1100`。取反是 `1110 0000 1000 0011`，也就是 0xe083。选项 A 是还没加回进位的低 16 位，选项 B 是加回进位但还没取反。

整份 UDP 还要先加上伪首部和首部。伪首部 12 字节：源 IP、目的 IP、一个 0、协议号 17、UDP 长度。它不出现在线上，用来检查这份报文是不是交给了正确的主机和正确的协议。长度字段是 UDP 首部加数据，不含伪首部。

奇数个数据字节时，计算用的最后一个字高 8 位是那个字节，低 8 位补 0。补的字节不传输，长度字段也不加它。`practice-check` 里数据 `41` 被看成 `0x4100`，线上仍然只有 1 个数据字节。

UDP 校验和可选。字段写成 0，表示发送方没算，接收方直接收下。如果反码求和再取反恰好是 0，必须改记成 0xffff，否则和「没算」分不清。`0.0.0.0` 那一组就是这样：取反得到 0x0000，线上写 `ff ff`。接收端把字段一起加回去，回卷后应当是 0xffff。不是 0xffff 就丢弃，UDP 不因此重传。

2018-39 的分用看目的端口。源端口只在对方要回信时有用，可以是 0。`header 06320045001CE217` 的目的端口是 0x0045 = 69，熟知端口，对应 TFTP；长度 0x001c = 28，数据 20 字节；源端口 0x0632 = 1586，所以是客户发给服务器。数据没给全，不能重算校验和。

2021-39 的效率是应用层字节除以传输层报文总长。12 字节数据：UDP 首部 8 字节，12/20 = 60.0%；TCP 首部最少 20 字节，12/32 = 37.5%。伪首部不在报文里。12 字节若把 12 字节伪首部也算进 UDP，总长变成 32，效率变成 37.5%，那是选项 A、B 里 UDP 那一格的来源。16.7% 是 12/72，多算了别的首部。

### 三次握手和四次挥手

客户从 CLOSED 发 SYN，进入 SYN_SENT。服务器原在 LISTEN，收到后进入 SYN_RCVD，回 SYN+ACK。客户收到后进入 ESTABLISHED，再回 ACK，服务器这才进入 ESTABLISHED。

三条规则就够算完全部序号题：

1. 确认号 = 对方这一段的序号 + 这一段消耗的序号数。
2. SYN 和 FIN 各消耗 1 个序号，即使没有数据。王道约定带 SYN 的段不携带应用数据。
3. 不带数据的纯 ACK 不消耗序号。第三次握手不带数据时，序号已经是 SYN 用掉之后的值，发完也不再加。

2011-39 的第二次握手必须 SYN=1 且 ACK=1，确认号是 11220+1 = 11221。服务器的初始序号自己选，和 11220 没有关系。题目问「可能是」，所以 seq=11221 是一种合法取值，四个选项里只有 C 同时满足标志位和确认号。B 的确认号漏了这 1。程序用 `open 11220 11221` 把这一段原样打出来。结果行里的第三次确认号是 11222，那是另一问。

2019-39 的第三次握手确认的是服务器的 SYN。服务器初始序号 2046，确认号 2047。2019 是第二次握手的确认号，方向反了。2046 是漏了加 1。

四次挥手按主动关闭的一方来写。客户先关：发 FIN 进入 FIN_WAIT_1，服务器进入 CLOSE_WAIT 并回 ACK；客户收到 ACK 进入 FIN_WAIT_2；服务器再发 FIN 进入 LAST_ACK；客户回 ACK 进入 TIME_WAIT，服务器收到后 CLOSED。TIME_WAIT 还要等 2MSL。两个理由：最后那个 ACK 若丢失，对方会重传 FIN，自己得还在；旧连接的报文段也要先从网络里消失。程序停在 TIME_WAIT，因为 2021-38 问的就是这一态，不是等完以后的 CLOSED。

2021-38 的客户是主动关闭方。收到对方 FIN 并发了 ACK 之后是 TIME_WAIT。CLOSE_WAIT 是被动方刚收到 FIN 的状态。FIN_WAIT_1 是自己的 FIN 刚发出去。FIN_WAIT_2 是自己的 FIN 已被确认、对方的 FIN 还没到。

双方同时发 FIN 时，在 FIN_WAIT_1 收到的是对方的 FIN 而不是自己的 ACK，进入 CLOSING，不是 FIN_WAIT_2。收到 ACK 后再进 TIME_WAIT。`close both` 按这个交错来。正常挥手和同时关闭的差别就在这一步。

第三次握手可以带数据。`open 1000 5000 data 200` 的数据从 1001 到 1200，下一序号是 1201。消耗的是这 200 个字节，不是再给 ACK 加 1。

### 确认号停在空洞前面

序号是本段第一个数据字节的编号。确认号是期望的下一字节，也就是连续收到的最后一字节加 1。后面的段到了、中间缺了一段，确认号仍然停在缺的那段的开头。这是累积确认。选择确认是后来的可选项，408 这几道题不按选择确认做。

2009-38：第一段 200～499，第二段 500～999，两段都到了，确认号 1000。500 只确认了第一段。700 和 800 是把长度直接相加、没按字节衔接。

2011-40：第 3 段序号是 900，它前面那段长 400 字节，所以第 2 段序号是 900−400 = 500，第 1 段是 500−300 = 200。第 2 段没到，确认号就是 500。1400 是把第 3 段的末尾也确认了。第 3 段占 900～1399，它到了也不能越过空洞。

2013-39：收到序号 1913、确认号 2046、100 字节。这一段占 1913～2012。我方下一序号就是对方的确认号 2046。我方确认号是 1913+100 = 2013。2012 是最后一个字节，还没加 1。2047 是把我方序号又加了 1，纯数据段的回复序号不加。

2020-39：SYN 用掉 1000，数据从 1001 开始。FIN 的序号是 5001，它自己占用 5001，数据是 1001～5000，共 5001−1001 = 4000 字节。4001 是忘了 SYN 占一个序号。4002 是把两端都算进了数据。`practice-fin` 用同两个数走了一遍：握手后下一序号 1001，再发 4000 字节，FIN 的序号就是 5001。

## 易错点

1. **进位要加回去再取反。** 2024-39 的 A 是丢掉进位，B 是还没取反。最后才取反。
2. **UDP 的 0 和 0xffff 不是一回事。** 字段 0 表示不检验。真算出 0 要改记 0xffff。TCP 没有「不检验」这一种，但第 01 关同样把算出的 0 写成 0xffff，因为校验和字段没有第二种编码。
3. **伪首部不传输，协议号是 17。** 把它当成 UDP 首部的一部分，2021-39 的 UDP 效率会算成 37.5%。长度字段也不含这 12 字节。
4. **奇数补 0 只存在于计算里。** 线上的长度和字节串都不含这个 0。补 0 时这一字节在 16 位字的高 8 位。
5. **分用看目的端口。** 源端口、长度、校验和都不用来把数据交给哪个进程。
6. **SYN、FIN 各占一个序号，纯 ACK 不占。** 2020-39 因此是 4000，不是 4001 或 4002。带 SYN 的段按王道不携带数据；第三次握手的 ACK 可以带，带了就只加数据字节数。
7. **2011-39 的服务器序号是自己选的。** 题干写「可能是」。确认号必须是 11221，标志位必须 SYN=1、ACK=1。seq=11221 只是一个合法例子，不是从 11220 推出来的。
8. **累积确认停在第一个空洞。** 2011-40 不能因为第 3 段到了就确认到 1400。两段都到了的 2009-38 用累积确认和用选择确认都会得到 1000，有的解析因此把这道题说成选择确认，下一道丢段的题就会算错。
9. **2013-39 不要把最后一字节当成确认号。** 确认号是 2013，不是 2012。我方序号用对方的确认号 2046，不要再加 1。
10. **TIME_WAIT 是主动关闭方的最后一态。** 被动方是 CLOSE_WAIT，然后 LAST_ACK，然后 CLOSED。同时关闭才是 CLOSING。FIN_WAIT_2 还没收到对方的 FIN。
11. **状态名的连字符和下划线是同一个状态。** 王道常写成 FIN-WAIT-1、CLOSE-WAIT。程序里用下划线，方便作为标识符。

## 概念卡片

### 传输层做什么

传输层在两台主机的进程之间提供逻辑通信，也就是端到端。网络层是主机到主机。这一层要复用和分用：多个进程的报文共用一个 IP，到达后再按端口交给对应进程。UDP 和 TCP 都做差错检测。可靠传输、流量控制和拥塞控制是 TCP 才有的，后两项在第 12 关。

### 端口

端口是传输层服务访问点。16 位。熟知端口 0～1023 分给固定的服务器程序，例如 DNS 53、DHCP 67/68、TFTP 69、NTP 123、SNMP 161、RIP 520。客户端一般用 1024 以上的短暂端口。分用只看目的端口。源端口告诉对方回信打到哪里，不需要回信时可以是 0。

### 无连接和面向连接

无连接：发送前不建立连接，每个报文独立选路，不保证到达、不保证顺序。UDP 是这一种。面向连接：先握手，通信期间维持状态，结束时释放。TCP 是这一种。IP 本身仍然是无连接的，TCP 的连接是两端传输层实体维持的逻辑连接，中间路由器看不见。

### UDP 和 TCP

| | UDP | TCP |
|---|---|---|
| 连接 | 无 | 面向连接，三次握手、四次挥手 |
| 可靠性 | 尽最大努力，校验失败就丢弃 | 序号、确认、重传 |
| 报文 | 面向报文，应用层交来的报文不合并、不拆开 | 面向字节流 |
| 拥塞控制 | 没有 | 有，第 12 关 |
| 首部 | 8 字节 | 最少 20 字节 |
| 校验和 | 可选，要加伪首部，协议号 17 | 必有，伪首部协议号 6 |
| 通信方式 | 一对一、一对多、多对一、多对多 | 一对一 |

UDP 适合一次就传完的短报文，以及宁可丢一点也不能等的实时流量。DNS、DHCP、TFTP、SNMP、RIP 用 UDP。需要字节流按序可靠到达时用 TCP。
